# C-2 충동구매 위험도 모델

결제 화면에서 이번 구매의 **충동구매 위험도(0~1)와 주요 이유**를 예측합니다.
4-1(`ai/features.py`, `ai/data/`)의 특성과 가상 데이터 방식을 이어받아, 지금 실제로 수집되는 값으로 다시 정했습니다.

```
데스크톱: 상품 화면 숫자(할인율, 압박 문구, 반복 방문, 머문 시간) ─┐
서버 DB: 금액 비율, 최근 결제 빈도, 과거 선택, 쿨다운 이력 ─────────┼→ 서버 check (PHP) → 위험도, 단계, 이유 → 팝업 문구
서버 시각: 시간대, 요일, 월급일 ──────────────────────────────┘        모델: ipp/model/risk_model.json
```

## 1. 한 행과 라벨

한 행 = **결제 화면 팝업 1건** (데스크톱이 결제 화면을 감지해 서버 `check`를 부른 순간). 열 정의는 [`schema.py`](schema.py).

| 팝업 결정 (`bl_decision`) | 담아두기 결과 | 라벨 |
|---|---|---|
| `buy` 그래도 구매 | | **1** |
| `hold` 조금 더 생각하기 | `failed` (쿨다운 중 결제) | **1** |
| `giveup` 안 살래요 | | **0** |
| `hold` | `success`, `gaveup` | **0** |
| `close` X 닫기, 결정 없음, `hold` + `waiting` | | 뺀다 |

- 4-1은 쿨다운 결과만 라벨이었고 실제 `failed`가 0건이었다. 팝업 결정은 결제 화면마다 생기므로 훨씬 빨리 쌓인다.
- 서버는 예측할 때 원시 값, 위험도, 모델 버전을 **숫자로만** 감지 기록에 남긴다 (C-2 3단계). 나중에 결정이 정해지면 그 행이 그대로 학습 데이터가 된다.

## 2. 특성

| 원시 값 | 출처 | 모델 특성 | 예상 방향 | 근거 |
|---|---|---|---|---|
| `hour` | 서버 시각 | 심야(23~4시), 늦은 저녁(21~22시) | 심야 ↑ | 4-1 README (자기통제 약화 가설) |
| `weekday` | 서버 시각 | 주말 | ↑ | 4-1 (가설) |
| `days_since_payday` | 서버 시각, 25일 가정 | 월급일 후 5일 이내 | ↑ | Stephens 2003. 가정값이라 약하게 |
| `amount` | check 결제 금액 | log(금액/1만) + 모름 표시 | | 절대 금액은 비율과 함께 넣어 비중을 모델이 정함 |
| `amount_ratio` | 서버: 이전 90일 결제 화면 금액 평균 | log(비율) | ↑ | 심리적 회계 (Thaler) |
| `discount_rate` | 데스크톱: 같은 쇼핑몰 최근 상품 화면 | 할인율/100 + 모름 표시 | ↑ | 할인이 '지금 사야 이득'이라는 느낌을 만든다 |
| `pressure` | 데스크톱: 상품 화면 OCR에 타임딜·품절임박·오늘만 등 | 0/1 | ↑ | 희소성·긴급성 (Cialdini) |
| `product_views_24h` | 데스크톱 메모리 | log(1+n) | ↑ | 4-1 방문 수 (계속 맴도는 마음, 가설) |
| `same_item_views_24h` | 데스크톱 메모리 (상품명 해시, 원문 저장 안 함) | log(1+n) | ↑ | 같은 상품을 되풀이해 보는 것 (가설) |
| `browse_sec` | 데스크톱: 상품 화면 처음 본 때 → 결제 화면 | log(분) + 모름 표시 | 짧을수록 ↑ | 즉시성 (Rook 1987), 빠른 판단 (Kahneman) |
| `checkouts_7d` | 서버: 직전 7일 결제 화면 감지 | log(1+n) | ↑ | 쇼핑 빈도 (가설) |
| `buy_rate` | 서버: 지난 팝업 결정 | '그래도 구매' 비율 | ↑ | 개인 성향. 기록이 적으면 전체 평균(0.35)으로 당김 |
| `cooldown_fail_rate` | 서버: 지난 담아두기 결과 | 실패 비율 | ↑ | 개인 성향. 평균(0.25)으로 당김 |

**뺀 것**: 업종(데스크톱은 쇼핑몰만 앎), 결제 화면 여부(예측 시점이 항상 결제 화면이라 늘 1).
**과거 기록 특성은 그 시점 이전 기록만** 쓴다 (미래 정보 누설 방지). 당기는 기준값은 `schema.RAW_PARAMS`에 있고 JSON에 함께 들어가 서버가 같은 값을 쓴다.

## 3. 가상 데이터

[`generate.py`](generate.py): 회원 300명, 180일, 결제 화면 6,000건 (seed 42).

- 회원마다 평소 결제 수준, 숨은 충동 성향, 하루 상품 화면 수가 다르다.
- 회원별로 **시간순**으로 만들고, 결정도 차례로 뽑는다. 그래서 과거 선택 비율·쿨다운 실패 비율·7일 빈도·금액 비율이 서버와 같은 규칙으로 '그 시점 이전 행'에서 계산된다. 숨은 성향은 과거 선택 비율을 통해서만 드러난다.
- 상품 화면 없이 결제 화면에 온 경우 20% (할인율·압박 문구·머문 시간 모름), 할인율을 못 읽은 경우 25%, 결제 금액을 못 읽은 경우 10%, X 닫기 8%, 기록 오류 3%.
- '그래도 구매' 확률은 2장의 예상 방향을 로지스틱 식으로 더해 정하고(`EFFECTS`), 전체 비율을 35%로 맞춘다.

## 4. 모델과 이유

- 표준화 + **로지스틱 회귀** (C=1, class_weight 없음). 위험도를 확률로 쓰므로 보정을 지키려고 클래스 가중치를 쓰지 않았다.
- 모름: 학습 평균으로 채워 표준화 값 0이 되게 하고, '모름 표시' 특성을 따로 둔다 (모름 자체가 정보일 수 있음. 예: 상품 화면 없이 바로 결제).
- **이유**: 특성별 기여 = 계수 × 표준화 값 = "평균적인 결제보다 위험을 얼마나 올렸나". 같은 group(예: 심야)끼리 더해 0.15 이상인 것을 큰 순서로. 문장은 서버(`ipp_risk_reason_text()`)가 만든다.
- 내보내기: `ipp/model/risk_model.json` (형식 `risk-logreg/1`). 특성 변환 규칙, 평균/표준편차, 계수, 원시 값 기준(`raw_params`), 서버 테스트용 예시 32개(`tests`: 원시 값 → 확률, 이유).
  [`model.py`](model.py)가 기준 구현이다. 서버 PHP와 C-3 예측 서버는 `tests`를 통과해야 한다.

## 5. 평가 (가상 데이터, 회원 단위 5겹 교차검증)

`python -m risk.evaluate` → `data/risk/report.md`

| 방법 | AUC | Brier |
|---|---|---|
| 지금 규칙 (심야 + 고액) | 0.590 | - |
| LR 서버 특성만 | 0.685 | 0.205 |
| LR 과거 기록 제외 | 0.678 | 0.206 |
| **LR 전체 (배포)** | **0.710** | **0.199** |
| 참고: 그래디언트 부스팅 | 0.682 | 0.207 |
| 모두 평균으로 예측 | 0.500 | 0.227 |

- 보정: 10구간 모두 예측 평균과 실제 비율 차이 0.02 이내
- 위험 단계 후보 (보통 ≥ 0.3, 높음 ≥ 0.55): 낮음 45% / 보통 40% / 높음 14%, 실제 그래도 구매 20% / 41% / 65%
- 이유: 0개 12%, 1개 27%, 2개 30%, 3개 이상 31%. 첫 이유는 금액 비율, 과거 선택, 심야 순
- AUC가 0.7 정도인 것은 일부러 넣은 노이즈와 회원 성향 때문이다. 효과를 크게 잡으면 얼마든지 올라가므로 숫자 자체에 의미를 두지 않는다

## 6. 한계 (발표에서 숨기지 않을 것)

1. **순환성**: 가상 데이터는 우리가 정한 효과로 만들었다. 모델이 그 효과를 다시 배울 뿐이므로 실제 성능의 증거가 아니다.
2. **'안 살래요'에는 포인트가 붙는다**: 포인트를 바라고 누른 '안 살래요'가 라벨 0에 섞이고, 과거 선택 비율 특성도 함께 오염된다. 나중에 mock 은행의 '24시간 뒤 실제 구매' 검증을 더 강한 라벨로 쓴다.
3. **팝업이 라벨을 바꾼다**: 위험도에 따라 팝업 문구가 달라지면, 그 문구가 결정(라벨)에 영향을 준다. 그래서 예측할 때 문구 단계와 모델 버전을 함께 기록한다.
4. **'그래도 구매' = 충동구매는 아니다**: 필요한 물건을 계획대로 사는 것도 '그래도 구매'다. 이 모델의 위험도는 "개입해도 살 가능성"에 가깝다.
5. **선택 편향**: 데스크톱이 감지한 결제 화면만 데이터가 된다 (모바일, 감지 실패는 빠짐).
6. **OCR 모름**: 할인율·결제 금액을 못 읽는 경우가 꽤 있다. 모름 표시로 다루지만 모름이 많으면 해당 특성의 힘이 약해진다.
7. **효과 크기와 월급일은 가정값**이다.

### 실제 데이터로 넘어가는 계획

1. 서버가 예측마다 원시 값을 기록한다 (3단계, SQL 010).
2. 결정이 쌓이면 실제 데이터로 **평가만** 먼저 한다 (가상 데이터 모델이 실제에서도 맞는지, 보정이 맞는지).
3. 충분해지면 실제 데이터로 다시 학습한다. 같은 JSON 형식이라 서버 코드는 바뀌지 않는다.

## 7. 실행 방법 (ai 폴더에서)

```powershell

```

## 개인정보

- 서버로 가는 데스크톱 값은 숫자와 0/1뿐이다. OCR 원문, 상품명, 주소는 보내지 않는다. 같은 상품 판단은 데스크톱 메모리의 상품명 해시로만 한다.
- 모델 JSON에는 계수와 평균만 있다. 회원 기록은 들어가지 않는다 (예시 `tests`는 가상 데이터 행).
- 가상 데이터와 평가 결과는 Git에 올리지 않는다 (`ai/data/risk/`).
